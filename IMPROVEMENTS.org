* Activity feed
** DONE Show author names in activity feed entries
:PROPERTIES:
:COMMIT: f2e6ff2
:END:

The ~activity.feed~ API provides ~author_user_id~ only in the ~:message~
sub-field. For ~thread_v2~ and ~dm~ activity types, data comes from
~bundle_payload~ instead, so ~(plist-get m :author_user_id)~ returned nil and
~(format "%s" nil)~ produced the string ~"nil"~.

Fixed by: using ~when-let~ in the parser so ~author-id~ stays nil, then at
render time falling back to the fetched message's ~user~ slot. Also added
type-specific prefixes ("Mentioned in", "Invited to").

** DONE Reuse ~slack-message-to-string~ for activity feed rendering
:PROPERTIES:
:COMMIT: 8e603c9
:END:

The activity feed had its own message rendering (custom header, ~slack-message-body~
only) that was inconsistent with channel buffers. Now it delegates to
~slack-message-to-string~ — the same function channels use — and just prepends an
activity context line ("Thread in #channel", "Mentioned in #ops-team", etc.).

This gives activity entries: profile images, colored author names, attachments,
reactions, thread info, and all future rendering improvements for free.

** TODO Show reactor as actor for message_reaction activities

Slack's activity feed shows the person who reacted as the card's author (e.g.
"Patrick — Reacted in #seo") and quotes the reacted-to message as context.
Emacs currently shows the reacted-to message with its original author (e.g.
"Pablo Stafforini — I'll set it up...") and appends "Patrick reacted with :+1:"
below.

To match Slack's presentation, ~message_reaction~ activities need a custom
rendering path instead of delegating to ~slack-message-to-string~:

1. Context header: "Reacted in #seo" (use reactor's name, not message author)
2. Actor line: reactor's avatar + name (from ~activity-reaction.user~)
3. Quoted message: the reacted-to message body (truncated, as context)
4. Reaction emoji display

This requires either a separate branch in ~slack-buffer-insert~ for reaction
activities, or a wrapper around ~slack-message-to-string~ that replaces the
header.

** TODO Fix 5-10 second delay when opening the activity feed

Every invocation of ~slack-activity-feed-show~ freezes Emacs for 5-10 seconds.
This is because the rendering path calls ~slack-message-get-or-fetch~ (which uses
~:sync t~) sequentially for each of the 20 activity items. Each uncached message
triggers a blocking API call.

Root cause chain:
1. ~slack-activity-feed-show~ calls ~slack-activity-feed-request~ (async, fine).
2. The callback creates the buffer and calls ~slack-buffer-init-buffer~.
3. ~slack-buffer-init-buffer~ loops over activities, calling ~slack-buffer-insert~
   for each.
4. Each insert calls ~slack-activity-message-to-string~ ->
   ~slack-message-to-string~ -> ~slack-message-get-or-fetch~.
5. ~slack-message-get-or-fetch~ does a synchronous API call if the message is not
   cached (~:sync t~).
6. 20 sequential sync calls x ~250-500ms each = 5-10 seconds of frozen Emacs.

*** Proposed fix: parallel prefetch

After receiving the activity feed response but before rendering, batch-fetch all
uncached messages in parallel:

1. Parse the activity items and collect all ~(ts, channel, thread-ts)~ tuples.
2. For each, check if the message is already cached via ~slack-room-find-message~.
3. For uncached messages, fire async ~conversations.history~ /
   ~conversations.replies~ requests in parallel.
4. Wait for all requests to complete (using ~accept-process-output~ with a
   timeout).
5. Store fetched messages in the room caches.
6. Then render all items — ~slack-message-get-or-fetch~ will now find everything
   in cache and return immediately.

This turns 20 sequential network round-trips into ~20 parallel requests resolved
in a single round-trip time (~300-500ms total).

An alternative: group items by channel and fetch a wider window of
~conversations.history~ per channel, reducing the number of API calls further.

* Channel loading delay / background prefetch
:PROPERTIES:
:SEVERITY: high
:END:

Opening any channel for the first time always takes a few seconds because it
fetches ~conversations.history~ synchronously. This is noticeable and makes
navigation feel sluggish.

** Proposed fix: background prefetch on connect

After WebSocket connection is established and the channel list is loaded, start
prefetching messages for channels in the background:

1. On ~client.userBoot~ completion, collect the user's channel list.
2. Prioritize: channels with unread messages first, then recently active
   channels, then the rest.
3. Fire async ~conversations.history~ requests (respecting rate limits) to
   populate each room's message cache.
4. When the user opens a channel whose messages are already cached, display is
   instant.

*** Rate limit considerations

Slack's ~conversations.history~ is Tier 3 (50+ req/min). With 20-50 channels,
prefetching completes in under a minute. Stagger requests to avoid bursts:

#+begin_src elisp
;; Pseudocode: prefetch with staggered timing
(let ((channels (sort-by-priority (slack-team-channels team))))
  (cl-loop for ch in channels
           for delay from 0 by 1.2  ;; ~50 req/min
           do (run-at-time delay nil
                #'slack-conversations-history ch team
                :limit "50" :after-success #'cache-messages)))
#+end_src

*** Scope

This is a significant architectural change. It affects:
- Memory usage (all channels' messages in RAM).
- Startup time (background work after connect).
- Rate limit budget (prefetch competes with user-initiated requests).

A lighter alternative: prefetch only channels with unreads, which is typically a
small subset and addresses the most common "I want to check my unreads" workflow.

* Stale reaction cache
:PROPERTIES:
:FILE: slack-message.el
:LINES: 347-382
:END:

** Problem

~slack-message-get-or-fetch~ returns a cached message immediately if found in
the room's message list, without checking freshness:

#+begin_src elisp
(or message          ;; cached version returned immediately
    (-some--> ...    ;; API fetch only if NOT cached
#+end_src

Reactions added after a message was cached are lost unless the channel buffer was
open when the ~reaction_added~ WebSocket event arrived. The WebSocket handler
(~slack-reaction-event.el:54-61~) only finds messages already in cache:

#+begin_src elisp
(cl-defmethod slack-event-find-message ((this slack-message-reaction-event) team)
  (let* (... (room (slack-room-find channel team))
             (ts (plist-get item :ts)))
    (when room
      (slack-room-find-message room ts))))  ;; nil if room not loaded
#+end_src

So: WebSocket ~reaction_added~ event arrives -> room not loaded -> message not
found -> reaction silently dropped -> cached message stays stale.

** Observed behavior

- Message in #benchmarking-data: ~:raised_hands: 1 :nice: 2~ renders (message
  cached with reactions, or buffer was open when reactions added).
- Message in #seo: ~:+1: 1~ does not render (message cached before reaction was
  added, buffer not open when WebSocket event arrived).

** Possible fixes

1. *Fetch-on-display*: when ~slack-message-get-or-fetch~ finds a cached message,
   still fetch reactions from the API and merge them. Downside: extra API call on
   every display.
2. *Store WebSocket events for unloaded rooms*: buffer reaction events and replay
   them when the room is loaded. More complex but no extra API calls.
3. *Invalidate cache on WebSocket events*: when a ~reaction_added~ event can't
   find the message, mark the room as needing refresh. Next time the room is
   opened, fetch fresh data.
4. *Selective refresh*: only re-fetch the specific message (by ts) when a
   reaction event targets an unloaded room. Lightweight and targeted.

Option 4 seems best: on ~reaction_added~ for an unloaded room, fetch the single
message via ~conversations.history~ with ~latest=ts, inclusive=true, limit=1~ and
update the room's message cache. This also helps with other stale-cache
scenarios (edits, deletions).

* Synchronous blocking calls
:PROPERTIES:
:FILE: slack-message.el
:LINES: 347-382
:END:

~slack-message-get-or-fetch~ uses ~:sync t~ for ~slack-conversations-replies~ and
~slack-conversations-history~. This blocks Emacs completely until the API
responds. The file itself has a TODO noting this:

#+begin_example
;; TODO this block is time consuming! We could retrieve these messages
;; in parallel using the same waiting mechanism (accept-process-output,)
;; but waiting on the list of messages.
#+end_example

The activity feed renders 20 items sequentially, each potentially making a
synchronous API call. This can freeze Emacs for several seconds.

** Possible fixes

1. Prefetch messages in parallel before rendering (batch
   ~conversations.history~ calls, wait for all, then render).
2. Render incrementally: show placeholder text, fetch async, replace when ready.
3. Use ~conversations.history~ with a wider window to fetch multiple messages per
   room in a single call, then distribute to activity items.

* Deprecated API usage
** Stars/saved items (~slack-star.el~)

Comment at line 35 explicitly says the stars API moved to ~saved.list~ in July
2023. The code still works but uses deprecated terminology and may break if Slack
removes the old endpoint.

** Reminders (~slack-reminder.el~)

Slack deprecated the reminders API (July 2023). Should migrate to ~saved.list~
for "save for later" functionality. Current code references the changelog but has
no migration.

* Token handling fragility
:PROPERTIES:
:FILE: slack-request.el
:LINES: 215-237
:END:

Hard-coded list of endpoints that require enterprise vs team tokens. A comment in
the code warns: "which token is required for an endpoint may change arbitrarily
at any time." No dynamic discovery or version check mechanism.

* Missing nil checks and silent error suppression
:PROPERTIES:
:SEVERITY: medium
:END:

Multiple places use ~ignore-errors~ to silently swallow failures:

- ~slack-activity-feed-buffer.el:174~ — room name lookup
- ~slack-message-formatter.el:178~ — message body processing
- ~slack-block.el:1323~ — block formatting
- ~slack-message-reaction.el:66~ — reaction creation

These hide real bugs. Prefer ~condition-case~ with explicit error logging.

* Image cache unbounded
:PROPERTIES:
:FILE: slack-image.el
:END:

Image cache files accumulate in the temp directory with no size limit or cleanup
policy. Heavy image usage could consume hundreds of MB over time.

* Mark-as-read optimistic update
:PROPERTIES:
:FILE: slack-message-buffer.el
:LINES: 147
:END:

~conversations.mark~ is called asynchronously but ~last-read~ is set
optimistically without waiting for the API response. If the API call fails, UI
state is inconsistent with the server. Should add a failure callback that reverts
the local state.

* Block types not implemented
:PROPERTIES:
:FILE: slack-block.el
:LINES: 103-110
:END:

Two TODO comments for unimplemented block types. These render as empty strings,
meaning some message content is silently dropped.

* Rate limiting not abstracted
